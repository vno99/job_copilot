# CLAUDE.md

Ce fichier fournit des instructions à Claude Code (claude.ai/code) lors de l'utilisation du code dans ce dépôt.

## Aperçu

Ce projet est un système automatisé de mise en correspondance d'emplois et de recomposition de CV orchestré par Apache Airflow. Le pipeline automatique enchaîne : scraping d'offres (Hellowork) et ingestion en base PostgreSQL. Le profil candidat est **uploadé via l'API** (`POST /api/v1/profiles`), et le **matching** ainsi que la **génération de CV recomposés (Markdown via LLM) sont déclenchés à la demande** (interface de validation).

## Architecture

### Orchestration et Infrastructure
- **Apache Airflow** : orchestre le pipeline automatique via deux DAGs :
  - `dags/job_copilot.py` (hellowork : scraper → ingestion, **le matching et la génération de CV sont à la demande**). Code conservé mais **DAG mis en pause** (l'agent de recherche le remplace à terme ; le RAG hellowork est considéré obsolète).
  - `dags/search_parameters_agent.py` (**agent de recherche**, actif) : toutes les heures (`0 * * * *`), lit `search_parameters` et ingère, pour chaque paramètre, les offres de son URL via `URLJobIngestorService.run(url, max_offers)` — le même pipeline que l'ajout par URL dans l'UI (matching/CV/lettre immédiatement disponibles). Pas de pagination, `max_active_runs=1`. Il utilise le `CeleryExecutor` avec Redis comme broker et PostgreSQL pour les métadonnées.
- **Docker Compose** : orchestre la pile (scheduler, worker, webserver, etc.), PostgreSQL et Redis. Le service `postgres-data` (port 5434) est la **base applicative** ; le service `postgres` est la base de métadonnées Airflow.
- **API de validation (`api/`)** : API FastAPI (upload de CV, matching, sélection, génération de CV à la demande, ajout d'offres par URL `POST /api/v1/job-offers/from-url` — avec champ `source` optionnel pour le contenu collé, exécution de l'agent de recherche via `POST /api/v1/search-parameters/run` — toutes les recherches **actives** — et lancement unitaire d'une recherche via `POST /api/v1/search-parameters/{id}/run` — une ligne précise, **même inactive**, `404` si inconnue, activation/désactivation des paramètres via `PUT /search-parameters/{id}/activate` / `/deactivate`). Au démarrage (lifespan), elle applique `ensure_schema` (idempotent) : la base de dev reste toujours à jour avec `sql/tables.sql`, sans migration manuelle après un changement de schéma. Contrat complet dans `docs/api-contract.md`.
- **Interface web (`web/`)** : application Next.js — profils, offres (actives et archivées ; tableau triable avec colonne **Source** à droite de Contrat, filtres **Entreprise** et **Source** débouncés), détail d'offre (matching, génération de CV et lettre, export PDF du CV, copie de la lettre), ajout d'offres (modale à **formulaire unique** : URL + slider « nombre maximal d'offres » 1→20 défaut 5, **désactivé** dès qu'un **contenu de page collé** (champ optionnel « Contenu de la page ») est fourni — le contenu remplace le fetch Playwright, **offre unique**, l'URL n'est jamais récupérée et reste la clé de dédoublonnage), recherches sauvegardées (CRUD + colonnes « Max offres » et « Statut » avec toggle d'activation par ligne — une recherche inactive est ignorée par l'agent) avec bouton **« Exécuter »** qui déclenche immédiatement l'agent (`POST /api/v1/search-parameters/run`, même pipeline que le DAG) et affiche le résumé de l'ingestion (offres ajoutées / déjà présentes, échecs par catégorie), et un **triangle vert par ligne** (colonne « Lancer ») pour le lancement unitaire de cette recherche (`POST /api/v1/search-parameters/{id}/run`), **même si inactive** (test ponctuel, `is_active` inchangé) — la bannière de résultat est enrichie du **titre** et de la **source** de la recherche. Pas encore de tableau de bord côté front (la route API `/stats` l'alimente).

### Racine applicative : `src/`
Toute la logique vit sous `src/` (paquets avec `__init__.py`, imports fiables) :

- **`src/interfaces/scrapers/hellowork/scraper.py`** : scraper Hellowork (adaptateur vers une source externe). Écrit des offres brutes en JSON dans `data/hellowork/`. Chemin d'import stable, utilisé par les tests et le DAG.
- **`src/interfaces/scrapers/url/scraper.py`** : récupération d'une page web pour l'ajout d'offre par URL (`URLScraper.fetch_text`, Playwright headless + lxml pour HTML→texte ; `normalize_url` valide http/https — barrière SSRF minimale). La conversion HTML→texte préserve la structure des blocs (paragraphes, listes à puces préfixées « - ») via `src/core/html_text.py` (`element_to_text`) : le LLM d'extraction voit la mise en page et la retranscrit dans la description — une offre affichée en blocs ne doit pas arriver aplatée en un seul paragraphe. Elle réinjecte aussi les **`href`** de la page (résolus en URL absolues, avec leur texte d'ancre, section `LINKS DE LA PAGE`) : sans eux, les URLs des offres d'une liste seraient perdues par la conversion en texte et le LLM répondrait « page sans offre » (422). Les liens des conteneurs **secondaires** (`nav`/`header`/`footer`/`aside` — navigation, pied de page, barre latérale, carrousels « dernières offres » logés dans le header) sont **exclus** de la section : leur injection plaçait en tête de liste des URLs d'offres hors critères de recherche (ex. le carrousel « dernières offres » du header Free-Work, trié par date) que le LLM, invité à renvoyer les URLs « dans l'ordre de la page », sélectionnait en priorité. **Exception** : un `<header>` **imbriqué dans le contenu principal** (`main`/`section`/`article`) est du contenu, pas du chrome — Hellowork enveloppe ses cartes de résultats dans un `<header>` à l'intérieur de la `section` de résultats ; l'exclure retirait toutes les URLs d'offres de `LINKS DE LA PAGE` et le LLM inventait des URLs slug (404 à la récupération individuelle). `nav`/`footer`/`aside` restent toujours exclus, où qu'ils soient (`NESTED_IN_CONTENT_ALLOWED_TAGS`). **Limite connue** : les sites protégés par un anti-bot (Indeed — Cloudflare Turnstile interactif —, APEC — DataDome, les API `/cms/webservices/offre/*` renvoient 403 au headless et la page affiche « l'offre n'est plus disponible ») bloquent le navigateur headless → la page renvoyée n'est pas une offre → `URLScrapingError` (422), sans contournement implémenté.
- **`src/services/`** : services applicatifs (orchestration d'un use-case) :
  - `job_parser.py` : lecture des JSON scrappés → normalisation (1:1 sur la table `job_offer`) → upsert avec dédoublonnage sur `content_hash`.
  - `profile_parser.py` : parsing d'un CV uploadé (Markdown/HTML) → `candidate_profile` (nouvel id à chaque upload).
  - `job_analysis.py` : matching offre × profil **via LLM** (score, forces, faiblesses, compétences manquantes, explication personnalisée) → `match_result`. Le LLM reçoit le **CV brut anonymisé** (`build_score_profile` → `raw_cv`), pas une structure parsée. Exige `OPENROUTER_API_KEY` (pas de fallback).
  - `cv_generator.py` : génération de CV recomposé **via LLM** (recomposition du CV brut anonymisé en Markdown, coordonnées réinjectées côté serveur) → `cv_version`. Exige `OPENROUTER_API_KEY` (pas de fallback).
  - `letter_generator.py` : génération de lettre de motivation **via LLM** en **deux passes** (depuis l'offre et le CV généré, sinon le CV brut ; anonymisation, lettre **anonyme** — aucune coordonnée réinjectée) → `letter_version`. La pass 1 (rédaction) exige `OPENROUTER_API_KEY` ; la pass 2 (réécriture « humaine ») est best-effort : un échec conserve la lettre de la pass 1.
  - `url_job_ingestor.py` : ajout d'offres par URL (`URLJobIngestorService.run(url, max_offers)`, `URLOfferDuplicateError` → 409) — normalisation de l'URL, fetch Playwright, classification LLM de la page (`extract_page`). **`run_from_source(url, source_text)`** (champ `source` de `POST /job-offers/from-url`) : même ingestion **offre unique** mais le contenu collé **remplace le fetch Playwright** — converti en texte (`_source_to_text` : HTML → `URLScraper._html_to_text`, texte brut → tel quel, borné à `MAX_PAGE_CHARS`) puis extrait par `extract_offer` (mono-offre, une liste collée répond 422) ; l'URL n'est **jamais récupérée** (clé de dédoublonnage + source = domaine, borne `SOURCE_MAX_CHARS=2_000_000` → 413 côté route — généreuse car un code source embarque styles + JavaScript, le texte réellement soumis au LLM reste borné à `MAX_PAGE_CHARS=12_000` par la conversion). Débloque les sites anti-bot (Indeed/APEC) sans contournement automatisé. **Offre unique** : contenu extrait par le LLM, dédoublonnage sur l'URL soumise (409 si déjà en base). **Liste d'offres** : le LLM renvoie les **URLs** uniquement ; celles déjà en base (colonne `url`, indépendamment de la source) sont **ignorées sans mise à jour**, puis chacune des `max_offers` offres **nouvelles** (1→20 défaut 5, dans l'ordre de la page) est récupérée individuellement (fetch Playwright + `extract_offer`) et ingérée via le pipeline existant (matching / CV / lettre immédiatement disponibles) — un échec individuel est ignoré (`added` peut être < `max_offers`). Le nombre d'URLs demandées au LLM est **borné au besoin** (`_urls_to_request` : 2 × `max_offers`, plancher 10, plafond `LIST_MAX_URLS=50`) pour que la sortie reste sous le budget de tokens d'extraction sur les pages aux URLs longues (ex. Indeed, tracking `pagead/clk` de ~350-500 caractères). `URLIngestResult` expose les clés de dédoublonnage (`keys`, paires `(source, source_job_id)`) et les compteurs `added` / `already_present`. Le 409 ne concerne que le chemin **offre unique** (la page EST l'offre) ; une liste dont toutes les offres sont déjà en base renvoie `added: 0` sans erreur.
  - `search_parameters_agent.py` : agent de recherche (`SearchParametersAgentService`, appelé par le DAG `search_parameters_agent`). `run()` lit `search_parameters` (`list_all`), **filtre les paramètres inactifs** (`is_active`), puis pour chaque paramètre actif appelle `self.ingestor.run(param.url, param.max_offers)`. `run_parameter_by_id(id)` (route `POST /search-parameters/{id}/run`) exécute **une** recherche via la même logique partagée (`_process`, une entrée du résumé) **sans filtrer `is_active`** — lancement unitaire depuis l'UI (test ponctuel, le statut est inchangé) ; lève `ValueError` (→ 404 côté route) si l'id est inconnu. Résumé JSON-sérialisable (XCom) : `{total, succeeded, duplicates, scraping_failed, llm_failed, other_failed, added_offers, already_present, parameters[]}` — chaque entrée expose `id`, `title`, `source`, `url`, `max_offers` (bannière d'un run unitaire dans l'UI). Erreurs rattrapées **par paramètre** (une URL en échec ne tue pas le run : `URLOfferDuplicateError` / `URLScrapingError` / `LLMExtractionError` comptées, `Exception` → `logger.exception`). Session de lecture courte fermée avant le traitement (l'ingestor gère ses propres sessions).
- **`src/core/`** : logique pure et réutilisable.
  - `domain/` : entités (`JobOffer`, `CandidateProfile`).
  - `html_text.py` : conversion HTML→texte préservant la structure (`element_to_text`) — retours à la ligne aux frontières de blocs (paragraphes, listes à puces préfixées « - »), `<br>` → `\n`. Partagé par les scrapers d'URL et Hellowork pour que la mise en page d'une offre survive à la conversion en texte.
  - `privacy/anonymize.py` : anonymisation d'un CV (`anonymize_cv`) — retire nom, téléphone, email, code postal + ville, LinkedIn avant envoi au LLM. Le nom est **validé** (`_leading_name` — préfixe de 1-3 mots capitalisés hors mots courants) : un intitulé de poste passé en `name` (ex. `profile.headline` = titre en gras du CV, ou une ligne combinée « Nom — Poste ») ne désactive pas la détection automatique (`_extract_name` ne retient que les lignes ressemblant à un nom) — le vrai nom du candidat ne doit pas fuir vers le LLM. La version stockée (`raw_content`) reste intégrale. Fournit aussi `extract_contact_info` / `inject_contact_info` pour la génération de CV (capture des coordonnées réelles avant anonymisation, réinjection dans un en-tête serveur après génération) et `clean_letter_markdown` pour la lettre de motivation (retrait de l'identité et des placeholders résiduels, **aucune réinjection** : la lettre reste anonyme).
  - `scoring/llm_matcher.py` : matching LLM (`compute_llm_match`, via OpenRouter → `OPENROUTER_LLM_MODEL_SMALL`) → score + `score_breakdown` + forces/faiblesses/compétences manquantes/`explanation`. Le profil reçu est le CV brut anonymisé (`raw_cv`). Lève `LLMMatchingError` (→ HTTP 502) si le LLM est indisponible.
  - `scoring/url_offer_extractor.py` : classification d'une page web — `extract_page(page_text, max_urls=50)` (instance dédiée `URL_SCRAPER_LLM`, via OpenRouter → `OPENROUTER_LLM_MODEL_SMALL`) renvoie un `PageResult` : `page_type` `"single"` (la page EST une offre, `offer` = contenu complet normalisé) ou `"list"` (le LLM ne renvoie que les **URLs** des offres, dans l'ordre de la page, au plus `LIST_MAX_URLS=50` — pas de contenu, chaque offre est récupérée individuellement ensuite). Le prompt repose sur le principe **contenu principal vs contenu secondaire** (règle 0) : seul le contenu principal détermine le type de page — **détail** (offre unique, offres similaires en bas secondaires et ignorées, jamais classée `list` même avec beaucoup de liens) ou **liste** (cartes sans « Description du poste », classée `list` **par sa fonction**, même à une seule offre). Le contenu secondaire (similaires, navigation, pied de page) ne contribue jamais à l'offre extraite. La règle `description` du prompt exige de retranscrire **tout** le texte de l'offre (missions, salaire, avantages, référence) sans résumer ni omettre de section — en **conservant la mise en page** (paragraphes, listes à puces, retours à la ligne) — et sans copier les offres similaires. `extract_offer(page_text)` = wrapper mono-offre : `extract_page(..., 1, single_only=True)` — le prompt mono-offre n'offre **pas** d'option « list » (une page de détail avec offres similaires ne doit pas être classée en liste), erreur si `page_type != "single"`. Parsing tolérant : un dict d'offre seul sans `page_type` est traité comme `single` ; la clé des URLs d'une liste peut être **`offers` ou `offres`** (le LLM écrit parfois la clé en français — cause racine d'un 422 intermittent, les deux sont acceptées). Lève `URLScrapingError` (→ 422) si la page n'est pas une offre — le message peut préciser le motif via le LLM (`reason`, ex. « l'offre n'est plus disponible sur le site ») —, `LLMExtractionError` (→ 502) si le LLM est indisponible **ou si la réponse JSON est invalide** : la troncature est détectée via `finish_reason`/`stop_reason` (`"length"`) et signalée (« réponse LLM tronquée »), avec un log du contexte brut (longueur, position, fenêtre de caractères) pour le diagnostic. Les URLs d'une liste sont **réellement fetchées** par le service : la barrière SSRF est exercée à l'exécution par `URLScraper.fetch_text` (un fetch refusé → offre ignorée).
  - `scoring/cv_generator_llm.py` : génération de CV par LLM en **une passe** (`humanize_cv_markdown` → `generate_cv_markdown`) → Markdown **recomposé** avec **fidélité factuelle stricte** : le CV original anonymisé est l'unique source de vérité — **Recomposition ciblée** : réorganiser, condenser et reformuler légèrement les informations **déjà présentes** dans le CV socle pour mettre en avant celles les plus pertinentes pour l'offre, sans modifier les faits, le niveau de preuve, l'identité professionnelle, les responsabilités ou le niveau d'expertise du candidat ; **aucune invention** (compétence, chiffre, résultat, impact), chiffres et résultats **uniquement** ceux déjà présents dans le CV, niveau de responsabilité/expertise/maîtrise jamais augmenté (anti-bullshit ATS) et **fidélité sémantique** : échelle mentionnée → utilisée → expérience → spécialisation → expertise (la présence d'une technologie ne prouve jamais une capacité ni l'agrégation non documentée de technologies en une capacité ou architecture — niveau de preuve exigé pour toute affirmation), résumé construit exclusivement sur le CV et pas plus ambitieux que le résumé source, pas de démonstration de pertinence pour l'offre (aucun lien argumentatif non documenté CV ↔ offre), matching = priorisation uniquement, titre recomposé seulement s'il reste factuellement compatible avec le parcours. **Portée de la recomposition** : conserver toutes les expériences et toutes les informations factuelles du CV socle (aucune expérience supprimée) ; la recomposition porte principalement sur titre, résumé professionnel, ordre des compétences, ordre des projets, formulation de certaines réalisations, visibilité relative des technologies — pas de note/justification hors CV. Le CV anonymisé est transmis **intégralement** (placeholders `[NOM]`, `[EMAIL]`…, coordonnées réinjectées côté serveur, **aucune troncature**), sur `CV_GENERATION_LLM` (via OpenRouter → `OPENROUTER_LLM_MODEL_LARGE`, instance dédiée — la lettre reste sur `OPENROUTER_LLM_MODEL_SMALL`). La **pass 2** (`_rewrite_cv_human`, réécriture « humaine » sur `HUMANIZE_LLM` via `OPENROUTER_LLM_MODEL_LARGE`) est **désactivée** : ses prompts `REWRITE_*` et le code sont conservés pour un usage futur mais **jamais appelés**. `humanize_cv_markdown` lève `CVGenerationError` (→ HTTP 502) si le LLM est indisponible, pas de fallback.
  - `scoring/letter_generator_llm.py` : génération de lettre de motivation par LLM en **deux passes** (`humanize_letter_markdown`) → Markdown (objet, corps, formule de politesse ; **aucune coordonnée** dans la lettre générée, anonyme). Pass 1 = `generate_letter_markdown` (historique, inchangé, sur `GENERATION_LLM` via `OPENROUTER_LLM_MODEL_SMALL`) ; pass 2 = `_rewrite_letter_human` (réécriture « humaine » systématique) sur l'instance dédiée `HUMANIZE_LLM` (via `OPENROUTER_LLM_MODEL_LARGE`, indépendante du modèle de génération). Aucune troncature du CV. La pass 1 lève `LetterGenerationError` (→ HTTP 502) si le LLM est indisponible ; un échec de la pass 2 conserve la lettre de la pass 1.
  - `scoring/score_engine.py` : extraction LLM des compétences (`extract_skills` à l'ingestion), instances `LLM` (matching, via `OPENROUTER_LLM_MODEL_SMALL`), `GENERATION_LLM` (lettre pass 1, `max_tokens=4096`, via `OPENROUTER_LLM_MODEL_SMALL`), `CV_GENERATION_LLM` (génération de CV pass 1, via `OPENROUTER_LLM_MODEL_LARGE`), `HUMANIZE_LLM` (pass 2 de la **lettre** uniquement — le CV est mono-passe, son `_rewrite_cv_human` est désactivé ; via `OPENROUTER_LLM_MODEL_LARGE`) et `URL_SCRAPER_LLM` (extraction d'offre depuis une URL, via `OPENROUTER_LLM_MODEL_SMALL`, `max_tokens=16000` — budget de sortie généreux car une **liste** reproduit les URLs des offres, ~350-500 caractères sur Indeed : `max_tokens` est un plafond, pas une injonction, la sortie réelle reste proportionnelle au nombre d'URLs demandées, borné par le service), et utilitaires partagés (`normalize_text`, `skills_to_names`, `offer_skills`).
- **`src/infrastructure/db/`** : couche d'accès PostgreSQL (SQLAlchemy).
  - `models/` : modèles ORM, reflet exact de `sql/tables.sql`.
  - `repositories/` : upserts (dialecte PostgreSQL) et requêtes métier — `existing_urls` (URLs d'une liste déjà présentes par colonne `url`), `get_by_keys` (refetch des offres persistées par paires `(source, source_job_id)`), `search_parameters_repository.get_by_id` (lecture d'une ligne pour le lancement unitaire).
  - `session.py` : engine + `session_scope()` ; `get_engine()` retourne l'engine courant et `configure_database(url)` le re-pointe (utilisés par les tests d'intégration).
  - `bootstrap.py` : `ensure_schema()` applique `sql/tables.sql` (idempotent).
- **`src/config/`** : `settings.py` (variables d'environnement : `DATABASE_URL`, chemins, mots-clés), `scoring.yaml` (seuil de génération de CV `match_threshold`). L'extraction des compétences, le matching, la génération de CV ET de lettre de motivation et la classification/extraction d'offre depuis une URL se font via **OpenRouter** (`score_engine.extract_skills`, `llm_matcher.compute_llm_match`, `cv_generator_llm.generate_cv_markdown`, `letter_generator_llm.humanize_letter_markdown`, `url_offer_extractor.extract_page` / `extract_offer`, clé `OPENROUTER_API_KEY` dans `.env`).

### Couche de données
- **PostgreSQL applicative** (service `postgres-data`) avec le schéma défini dans `sql/tables.sql` :
  - `job_offer` : offres analysées, compétences extraites (`skills_extracted`) et payload brut (`raw_payload`). Dédoublonnage sur `UNIQUE(source, source_job_id)` et `content_hash`.
  - `candidate_profile` : profils uploadés (`skills`, `experiences`, `education`, `cv_raw_json` porteur de `source_path` et du contenu brut `raw_content`, `is_active` — un seul profil actif garanti par un index unique partiel). Les métadonnées `experience_years` / `preferred_contracts` / `location` ne sont **plus extraites** (ni affichées, ni scorées).
  - `match_result` : scores, détail (`score_breakdown`), forces, faiblesses, compétences manquantes.
  - `cv_version` : CV recomposé généré, **un seul par couple (offre, profil)** — une nouvelle génération remplace l'existant (upsert sur `uq_cv_version_pair`), sans notion de version (`cv_content_json` = `{"markdown": …}`, `cv_text` = Markdown généré). `application_submitted` : suivi « candidature envoyée » (booléen par couple, basculé par `PUT /cvs/{id}/submitted`, **préservé à la régénération** du CV, revertible au re-clic dans l'interface). **Aucun stockage sur disque** : le CV n'est persisté qu'en base. Export PDF à la demande via `GET /cvs/{id}/pdf` (xhtml2pdf), jamais stocké.
  - `letter_version` : lettre de motivation générée, **une seule par couple (offre, profil)** — une nouvelle génération remplace l'existante (upsert sur `uq_letter_version_pair`), sans notion de version (`letter_content_json` = `{"markdown": …}`, `letter_text` = Markdown généré). **Aucun stockage sur disque** : la lettre n'est persistée qu'en base.
  - `search_parameters` : paramètres de recherche alimentant l'agent (`title`, `source`, `url`, `max_offers`, `is_active`, `created_at`, `updated_at` ; URL unique `uq_search_parameters_url`). `max_offers` : entier **1 → 20**, défaut **5** (contrainte `chk_search_parameters_max_offers`) — nombre maximal d'offres récupérées par le DAG `search_parameters_agent` pour cette URL. `is_active` (défaut **TRUE**) : seul un paramètre **actif** est traité par l'agent (DAG et bouton Exécuter) ; la bascule se fait via `PUT /search-parameters/{id}/activate` / `/deactivate`. **Exception** : le lancement unitaire (`POST /search-parameters/{id}/run`) traite la ligne demandée **même inactive** (test ponctuel depuis l'UI, le statut est inchangé).

## Commandes de développement

### Environnement
- **Démarrer toute la pile** : `docker compose up`
- **Base applicative seule** : `docker compose up -d postgres-data`
- **Base + API + web** : `docker compose up -d postgres-data api web`
- **API seule (dev)** : `pip install -r api/requirements.txt && uvicorn api.app.main:app --reload` (depuis la racine, API sur le port 8000). Pour l'ajout d'offre par URL, installer aussi le navigateur headless : `playwright install chromium` (déjà fait dans le `api/Dockerfile`)
- **Front (dev)** : `cd web && npm run dev` (l'API est attendue sur `localhost:8000` ; le front proxy `/api/v1/*` vers l'API)
- **Arrêter l'environnement** : `docker compose down`
- **Appliquer le schéma** (idempotent) — l'API l'applique déjà au démarrage ; cette commande reste utile pour une base non servie par l'API (ex. un conteneur vierge, la prod) :
  ```bash
  python -c "from src.infrastructure.db.session import engine; from src.infrastructure.db.bootstrap import ensure_schema; ensure_schema(engine)"
  ```

### Tests
- Tests unitaires (aucune base ni Docker requis) : `python -m pytest tests/ -q -m "not integration"`
- Tests d'intégration (nécessitent Docker) : `python -m pytest tests/ -q -m integration`
- Suite complète : `python -m pytest tests/ -q`
- **Tests front** (vitest + Testing Library, depuis `web/`) : `npm test` (exécution unique) ou `npm run test:watch` (mode watch). Config dans `web/vitest.config.mts`, setup commun (`jest-dom`, nettoyage DOM) dans `web/src/test/setup.ts`, tests colocalisés sous `web/src/**/__tests__/`. `next/link` et `next/navigation` (useRouter) sont mockés dans les tests de composants.
- **Base de test jetable** : les tests d'intégration tournent contre un **conteneur PostgreSQL éphémère** (`postgres:16`), démarré par le fixture session-scoped `docker_postgres` (`conftest.py`) et détruit à la fin (`--rm`). Le fixture re-pointe l'engine via `configure_database`, applique le schéma via `ensure_schema`, puis arrête le conteneur en teardown. Docker indisponible → les tests d'intégration sont ignorés (`skip`). La base de dev (`postgres-data`/`job_copilot`) n'est **jamais** touchée.

### Profil candidat
- Les profils sont **uploadés via l'API** (`POST /api/v1/profiles`, multipart) : un CV (Markdown/HTML) → un `candidate_profile` avec un **nouvel id** (`ProfileParserService.run_from_content`). Le premier profil devient actif ; l'activation se change via `PUT /profiles/{id}/activate`. Le contenu brut est stocké dans `cv_raw_json.raw_content` et exposé par le détail de profil (`raw_content`).
- Gestion du cycle de vie : **renommage** `PATCH /profiles/{id}` (`{profile_name}`, `409` si nom pris), **activation** `PUT /profiles/{id}/activate` (désactive les autres), **désactivation** `PUT /profiles/{id}/deactivate`. Le **profil actif ne peut pas être désactivé** (`409`) : il faut d'abord activer un autre profil. **Pas de suppression** (le DELETE a été retiré).

## Structure du projet
- `src/` : logique applicative (interfaces, services, core, infrastructure, config).
- `api/` : API FastAPI de validation (upload de CV, matching, sélection, génération de CV).
- `web/` : interface Next.js (profils, offres, détail d'offre, ajout par URL).
- `dags/` : DAGs Airflow (`job_copilot.py` hellowork — **pausé** — et `search_parameters_agent.py` actif).
- `config/` : configuration Airflow et journalisation Python (`logging.yml`, `logger_config.py`).
- `sql/` : schéma de la base applicative (`tables.sql`, source de vérité).
- `data/` : offres scrappées (`hellowork/`).
- `docs/` : documentation — `api-contract.md` est le contrat de l'API.
- `tests/` : tests unitaires et d'intégration (marqueur `integration`).
- `docker-compose.yaml` : orchestration Docker (Airflow, PostgreSQL, Redis).
